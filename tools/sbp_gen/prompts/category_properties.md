你的工作是屬性與面向：讀完每個主軸編碼類別與支持它的證據，找出這個類別可以從哪個角度看它在人與人之間變化，把每個角度畫成一把兩端可觀察的尺。這是類別跟 Persona Matrix 軸候選之間原本缺的一層——紮根理論的層級是類別 → 屬性 → 面向，你現在做的是後面兩層。

## 屬性：這個類別的哪一面在變化

同一個類別底下，不同受訪者可能在好幾個不同的角度上表現出差異。每一個角度是一個屬性。以「號碼牌動線困惑」這個類別為例，至少可以看到三個不同的屬性：

| 屬性 | 面向（低端 ←→ 高端） |
| --- | --- |
| 對這套動線的熟悉程度 | 第一次遇到、要問人或看別人怎麼做 ←→ 來過幾次、覺得像自助餐廳一樣自在 |
| 遇到不確定時怎麼處理 | 直接開口問店員 ←→ 先觀察別人怎麼做再跟著做 |
| 對等候的感受 | 覺得被晾在外面等 ←→ 覺得像平常排隊一樣自在 |

這三個屬性都成立，是因為證據裡真的看得到不同受訪者在這三個角度上各自分散，不是同一件事換句話說三次。

## 一個類別可以有多個屬性，也可以只有一個

**不設下限，也不設上限。** 證據撐得起幾個屬性就寫幾個——如果一個類別的證據只支持得起一個角度的變化，就只寫一個，不要為了湊數硬造第二個、第三個。硬要每個類別都生出固定數量的屬性，會逼你把同一件事換句話說很多次，這正是主軸編碼提示詞已經在防的毛病：不能只是複述類別本身的定義。

反過來，也不要因為想省事就把兩個明明不同的角度硬併成一個屬性。「對這套動線的熟悉程度」跟「遇到不確定時怎麼處理」是兩件不同的事——一個人可能很熟悉動線但還是習慣先問人確認，兩者不必然綁在一起，該拆就拆成兩個屬性。

## 面向：屬性的兩端，各自帶設計後果

每個屬性寫成一把有兩端的尺：

- **兩端都是可觀察的行為狀態**，不是人格形容詞。「焦慮／冷靜」「被動／積極」「內向／外向」這類詞從證據裡看不出來，只是貼標籤；「第一次遇到、要問人」跟「來過幾次、覺得自在」才是能從證據直接判斷的行為狀態。
- **兩端各自寫出設計後果**：如果一個人站在這一端，服務設計該為他做什麼？這是必填欄位，不是問完就算了的判斷題——沒有寫進輸出欄位的規則，沒有人能事後查核這個判斷有沒有真的做過。
- **兩端寫不出各自不同的設計後果，就代表這條尺不該存在**——這時候不是硬填一個看起來合理的答案，是把這個屬性整個刪掉，不要產出。這跟 Persona Matrix 對「沒有證據支持的落點」的立場一樣：寧可明講沒有，不要編一個看起來合理的東西。

## 一個屬性算不算數：三個入場條件

寫下任何一個屬性之前，先過這三關。任一關不過就不要寫出來——不是寫出來再標弱，是不寫。

**一、描述人，不描述服務結果。** 屬性要講這個人帶進情境的需求、判斷方式或行為傾向，不是
這家店做得好不好。檢查方法：把這條屬性跟「換成另一家餐廳」放在一起，問這個人的位置還成不成立。

```
❌ 份量滿足感：吃不飽 ↔ 吃得飽          → 換一家店位置就反過來，量的是店
✅ 對飽足程度的要求：吃一點即可 ↔ 要明確吃飽 → 換一家店仍然成立，量的是人
❌ 動線清楚 ↔ 不清楚                    → 兩端描述同一家店的兩種狀態，不是兩種人
```

畫面上讀得到的常常是結果，要往前退一層找那個「什麼樣的人，會讓同樣的服務產生不同結果」：
「覺得份量少」往前是「對飽足程度的要求」，「覺得價格太貴」往前是「價格判斷時使用的參照
基準」。「滿意 ↔ 不滿意」「覺得貴 ↔ 覺得便宜」「困惑 ↔ 不困惑」一律是結果，不是屬性。

**二、兩端是同一個構念的不同位置。** 用這個問題檢驗：**一個人能不能同時高度符合左右兩端？**
可以的話，那就是兩條屬性被壓成一條。

```
❌ 用餐價值取向：重視便宜 ↔ 喜歡品牌體驗   → 一個人可以同時很在意價格又很在意品牌
❌ 遇到不確定怎麼處理：等別人講或看別人做 ↔ 自己問或事先看好
                                        → 混了觀察、詢問、事前準備、自行探索四種策略
✅ 到店前的資訊準備程度：現場再看 ↔ 事前先查 → 左右都在回答「決策前準備多少資訊」
```

**三、案例裡真的有變異。** 兩端都要有人，而且要跨至少兩個受訪者。全部落在同一端是「這個
差異不存在」；只有一個人有資料是「還沒得比」，兩者不同，不要混。

過了這三關才是候選。接下來的穩定性、與其他屬性的獨立性、兩端的設計後果決定它強不強，
那是研究者選擇時要看的事——弱的屬性可以存在，但要在區辨依據裡講明弱在哪。

**情境變項不是維度。** 午餐來／晚餐來、一個人／四個人、今天趕／今天不趕，這些同一個人
明天就會跑到另一端。除非資料顯示這個人跨不同場合反覆採取同一種模式，否則不要寫成屬性。

## 兩端要站在同一層級回答同一個問題

兩端通過「一個人能不能同時高度符合左右兩端」這關，不代表兩端寫得對稱——常見的毛病是一端寫成條件清單、另一端寫成單一判斷，讀起來像在回答兩個不同的問題。寫完兩端之後，先問自己：**這兩端合起來，是在回答同一個什麼問題？** 把這個問題寫出來，再檢查兩端是不是都直接回答它、用同樣的語法結構、同樣的抽象程度，不要一端具體列點、另一端籠統帶過。

```
❌ 加價正當性來源：價格、份量與便利先過關 ↔ 休息或氣氛可合理加價
   → 左端在回答「基本條件要先滿足什麼」，右端在回答「什麼理由可以加價」，不是同一個問題
✅ 價格接受的依據：餐點與便利值得這個價格 ↔ 休息與氣氛值得多花一些
   → 兩端都在回答同一個問題：「這個人用什麼理由判斷這筆錢花得值不值得」
```

## 名稱：用講行為的說法，不要名詞化

屬性名稱不能是「ＸＸ度」「ＸＸ性」「ＸＸ感」這類抽象名詞——「動線清晰度」「價格容忍度」把「他覺得貴但還是進來吃了」壓成一個抽象詞，主詞不見了，動作也不見了，之後的人只看到名稱，完全還原不出這是在講誰做了什麼。

寫成「對這套動線的熟悉程度」「覺得這個價格划不划算」這種講得出行為或判斷過程的說法，而不是壓縮成一個名詞。

## 區辨依據

每個屬性附一句話：為什麼這條尺真的分得開受訪者，不是所有人都落在同一端。這句話要講機制或行為模式，不要只是複述類別本身的定義。

## 輸出格式

只輸出一個 JSON 物件，鍵是 `properties`，每一項帶 `category_id`（這個屬性屬於哪個類別）、`name`（屬性名稱）、`pole_low`／`pole_low_design`／`pole_high`／`pole_high_design`（兩端與各自的設計後果）、`discriminating_basis`（區辨依據）、`evidence_refs`（支持這個屬性的證據 id）。不要輸出 `schema_version`、`case_id` 或 `id`——這些由呼叫端補上。
