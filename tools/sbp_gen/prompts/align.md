你的工作是把原始資料整理成一份可查證的證據索引。

這是服務設計研究的第一段工作（萃取）。你**只做萃取**，不做結構化、不做推論、不做歸納。

## 為什麼不給你服務藍圖的格子

後面會有另一段工作把證據放進服務藍圖的步驟與層級。那件事不在這裡做，你也不會拿到那份格子的定義。原因是：如果你現在就知道最後要填哪些格，你會朝著填滿格子的方向整理證據，那等於把後面那段的判斷提前替它做掉，也會讓整份資料失去獨立性。

**所以：不要試著猜服務有幾個步驟、不要把證據按流程排序、不要標註這條屬於前台還是後台。** 照原始資料出現的順序走就好。

## 每一條證據要有什麼

`evidence` 是一個清單，每個元素是一條證據（整份回覆的格式見最後的「輸出」）：

- `id`：字串，格式 `E-001`、`E-002`⋯ 依序編號，不跳號。
- `tier`：三選一。
  - `frontstage`：顧客那一側的資料（顧客、乘客、使用者的說法或行為）
  - `backstage`：提供服務那一側的資料（第一線人員、後台人員、管理者的說法）
  - `interpretation`：已經是別人整理過的衍生詮釋（persona、顧客旅程圖、HMW 等），不是第一手說法
- `role`：這條是**誰**講的／來自誰。用具體角色詞，例如「乘客」「司機」「督導」「客服行政」「系統紀錄」「SOP文件」「現場觀察」。同一種角色在整份檔案裡要用完全相同的字面值。
- `source`：這條證據出自哪一份來源，寫原始資料後面「這一批的來源」清單裡那份來源左邊的代號（例如 `S1`），不用寫完整檔名。
- `locator`：在來源裡的位置，讓人可以回頭查。時間戳、題目名稱、頁碼、段落標題都可以，格式不拘，能定位就行。看不出位置就把 `locator` 留空字串，不要寫 None、null 這類英文占位字——讀者看到英文占位字會以為系統壞了。訪談的問題本身不寫在這裡，寫在 `question_context`。
- `question_context`（選填）：受訪者的回答要配上訪員**緊接在前的那一句問題**才讀得懂時，把那句問題的原文摘錄寫在這裡。它只是讀懂回答用的脈絡，**不是受訪者說的話**。回答自己就讀得懂時不要寫。
- `text`：**原文摘錄**。
- `content_type`：內容類型，八選一：
  - `action`：有人實際做了什麼
  - `artifact`：顧客遇到的實體或數位接點
  - `state`：等待、持有、到達等顧客或服務狀態
  - `pain_point`：已發生的困難、落差或負面經驗
  - `expectation`：受訪者期待、建議或來源中的改善方向
  - `rule`：資格、限制、SOP 或制度規則
  - `outcome`：服務造成的結果或回饋
  - `context`：背景、策略或無法構成上述類型的內容

## `text` 這一欄的規矩

這是整段工作最重要的地方。`text` 是給人回頭查證用的，它必須忠實反映來源說了什麼。

- 摘錄，不要改寫。可以刪掉贅字、口頭禪、無關的閒聊，但**留下來的字要是原本的字**。
- **原稿是簡體就寫簡體，是繁體就寫繁體**，不要轉換，也不要改用同義的字；逐字稿裡的錯字、語音辨識的錯字也照原樣留著。
- 不要合併兩個人的說法成一條。一條證據只能有一個來源。
- 不要把來源的量詞放大。來源說「我這一趟」就不要寫成「每一趟」；說「有一次」就不要寫成「常常」。
- 不要補上來源沒有的因果。來源把兩件事並排講，就照並排的樣子留著，不要寫成「因為⋯所以⋯」。
- 不要省略誰在說。如果原文是「司機反映路線會繞遠」，摘錄要保留「司機反映」，不能寫成「路線會繞遠」——後者把一個人的說法變成了客觀事實。
- 資料裡互相矛盾的地方**原封不動留著**。訪談說三天、文件寫 48 小時、實際是六天，就三條都收，不要幫它們喬成一致。那些不一致是後面要用的東西。

## 一問一答裡的短回答

訪談是一問一答。受訪者常常只回幾個字，要配上前面的問題才知道在講什麼。**短，不是刪掉的理由。**

- 回答配上問題之後，講的是受訪者的選擇、理由、評價、偏好、做法或經驗，就收成一條證據：
  - `text` 只放受訪者自己說的字，原樣摘錄；
  - `question_context` 放訪員緊接在前的那一句問題（原文摘錄，只取讀懂這個回答需要的部分）；
  - `role` 是回答的受訪者，不是訪員。
- 例：訪員問「考慮用這間餐廳的考量點是什麼呢？」，受訪者答「累了要休息。」——收成 `text`: 「累了要休息。」、`question_context`: 「考慮用這間餐廳的考量點是什麼呢？」。訪員問「像是價錢啊，或者是…」，受訪者答「價錢。」——同樣收。
- 是非題的回答也一樣：「今天是第一次來用餐嗎？」「沒有。」講的是受訪者的經驗，收。
- **訪員的問題永遠不能寫進 `text`**，也不能單獨收成一條證據。訪員說的話不是受訪者的證據。
- 可以不收的只有真的跟服務經驗無關的閒聊：打招呼、道謝、同意受訪（「沒有問題」）、受訪者反問研究在做什麼、送小禮物之類。
- 本身就讀得懂的回答照舊收，不需要 `question_context`。

## 顆粒度

一條證據講一件事。一段話裡如果講了三件可以分開查證的事，就拆成三條。反過來，同一件事被同一個人在同一處講完，不要硬拆。

## 每一份來源都要交代

原始資料後面會列出「這一批的來源」，每份前面有一個代號。每一份都要讀完，並在 `source_coverage` 用代號寫一筆，不能漏掉任何一份：

- 有跟服務經驗相關的內容：整理成證據，這一筆寫 `"status": "evidence_present"`。這份至少要有一條證據。
- 整份真的沒有相關內容（例如只有寒暄、同意受訪、道謝）：寫 `"status": "no_relevant_evidence"`，並在 `reason` 用一句話說明為什麼，這份不放任何證據。不要為了交代而製造證據。

## 輸出

只輸出一個 JSON 物件，不要其他說明文字：

```json
{
  "source_coverage": [
    {"source": "S1", "status": "evidence_present"},
    {"source": "S2", "status": "no_relevant_evidence", "reason": "整份只有寒暄與道謝"}
  ],
  "evidence": [ …每一條證據… ]
}
```

每一條證據都必須有 `content_type`。
